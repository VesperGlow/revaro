# Kirikiroid2 Web runtime

Upstream: https://github.com/fenghengzhi/kirikiroid2-web
Commit: 2028cbccaa91498bd36f270d349ae711d0e8fed3
Runtime originally published at https://krkr2.fenghengzhi.com/ and imported from the locally available distribution. See ENGINE-LICENSE.txt for the complete upstream license notices; assets.zip retains font licenses. JSZip 3.10.1 retains its MIT license header.

Revaro adaptations: upstream shell extracted into external scripts/CSS to keep CSP; no analytics, CDN, manifest or PWA worker; manifest-controlled game source, exact XP3 entry, forced lazy ZIP mount with no full-download fallback; IndexedDB namespace per stored game; save restoration waits for engine FS initialization and releases its startup dependency once; reload never unregisters the main application's worker or clears its caches.

index.js includes the local generic SDL middle/right button mapping fix (the prior Revaro glue revision had SHA256 cf58bad2be094ab94d29e5da8e3eb028480f02f369df404f0a9bf2080e4ddac5) and the frame-queue hook; unmodified published index.js SHA256 ace6eca1625b214b87fd9f3959e9f555450cbe4c0fd88af4b93bd3b45962e4c8. vlfs.js and assets.zip are the published binaries. index.wasm has the Web input and text-decoding adaptations described below. No game files or game-specific patches are distributed here.

SHA256SUMS.json records imported and adapted files for auditing. Runtime and assets are bundled so users do not require a CDN or a separate game host. Source for the engine remains available at the upstream commit above. Engine/plugin compatibility is not guaranteed by integration tests.

## Revaro Web input adaptation

`input.js` is a player-only adapter. It forwards wheel input to the existing `TVPWindowLayer::onMouseScroll(Event*)`, retaining both Window and DrawDevice/Layer delivery. It does not replace wheel with a keyboard shortcut and does not patch or inject game scripts. A frame-scheduler hook drains a bounded wheel queue between normal JSPI ticks. Native modal input continues through the engine's nested modal event loop.

The pinned input adaptation is reproducible with `scripts/kirikiri/export-input-bridge.py` from the original WASM (SHA256 `bb5f92e3e66ddb94893f81fed92705b1d29ff82c393ad679e8fa402ce52c495a`). It adds exports `revaro_mouse_scroll` for existing function 14591 and `revaro_key_release` for existing TVPMainScene::onKeyReleased function 14688, and changes one Cocos-to-VK lookup byte (passive data segment 436, offset 44) from 0 to 13. That input step does not rewrite a function body. Apply the text-decoder step below afterwards. `CCGLViewImpl-emscripten.cpp` sends SDL_RETURN as Cocos KEY_ENTER(164), while `CCKeyCodeConv.cpp` previously dropped that enum; the lookup correction preserves the native key map, key state and event delivery. The Python audit reverses both steps and reconstructs the byte-identical original module and rejects unknown input versions.

The glue adaptation is reproducible with `--glue <previous-Revaro-index.js> --output-glue <output>`; that input must match SHA256 `cf58bad2be094ab94d29e5da8e3eb028480f02f369df404f0a9bf2080e4ddac5`. It changes only `runTick` to call the player queue before the original tick.

Window ABI metadata for this exact build comes from the pinned `MainScene.cpp` and its compiled constructors/destructors: `_currentWindowLayer` at 5858060; TVPWindowLayer vtable at 5101940; window paint width/height at offsets 860/864; Cocos design view at 652/656; native modal flag at 6503. The TVPMainScene singleton at 5858088 owns its Cocos UI node at offset 612; the Node getChildren virtual slot at 288 exposes the standard child vector. Nonempty engine UI forms receive native touch and Escape, and block game wheel dispatch. EventMouse cursor X/Y and scroll Y are float offsets 44/48/56. The adapter validates the active vtable, memory bounds and dimensions before use; these are engine-build offsets, never game IDs, scene sizes or dialogue coordinates. **An engine upgrade requires regenerating and validating this ABI, not copying these offsets to another release.**

The native game still owns story/log/menu state. The adapter only owns native-modal, focus, held-input and touch gesture state. It does not infer scenes from pixels or captions. Native right-click remains intact outside modal windows; a native modal receives Escape on right-click. Keyboard events are restricted to the focused player, browser shortcuts remain browser-owned, and held inputs are released on blur/visibility loss through both the SDL keyup and the existing native release path. The latter makes release immediate even if SDL processing is paused; its native pressed-bit guard prevents duplicate delivery.

Native engine canvas size and GL viewport stay unchanged. A modal is presented by copying its correctly fitted native viewport crop to a centered 2D presentation canvas, over the last complete parent frame. A single aspect-preserving scale (capped by the player bounds) enlarges text/buttons; pointer/touch coordinates use the inverse of that same crop. No game coordinates or fixed button locations are used. Touch taps produce one mouse pair, vertical drags produce native wheel steps, and long/two-finger taps produce native right; touch-only buttons offer Back/Log/Enter.

Direct-share UI: no password/verification page or browser capability preflight. The authenticated management API reads ZIP directory metadata through FileAccess for a user-selected XP3 entry. Actual engine/graphics failures remain visible.

## Mixed legacy text encodings

`scripts/kirikiri/fix-text-decoder.py` consumes the input-adapted module (SHA256 `86c91161d26e5300bfb812b25b79fec03e0a35d6bd6d2545581cd188c6acd99c`) and produces the bundled module (SHA256 `0b585e23f60c251cbe62ac8557ad31accc279be15798ecd4ac3eb66c5c6905aa`). The equivalent C++ source change is distributed as `scripts/kirikiri/text-decoder.patch` against `cpp/core/base/TextStream.cpp`.

The original automatic SJIS → UTF-8 → GBK detection stored a successfully detected UTF-8/GBK converter in the global default. Later files then used it strictly, even when their encoding differed. The fix replaces only those two ten-byte stores in function 15501 with same-length WASM nops. The constructor's original body at offset 8787148 has length 4234 and SHA256 `56b0ed5d27554c6abece79ad3a67d20fa2c8d7f7030f2df5bbae659203068f69`; store sites are 8789255/8789284, global converter address 5847640, converter table slots 6856/6857. No function indices, sizes, memory layout, game bytes, ZIP loading or save paths change.

Automatic detection now runs independently for each BOM-less file. BOM handling, fallback order and explicit `Scripts.textEncoding`/`Storages.setTextEncoding` selections retain their original behavior. Ambiguous byte sequences can still decode as the wrong language; this is not universal encoding detection.

Actual local Chromium check with the supplied Sharin no Kuni Chinese archive: previously converter slot 6857 (GBK) remained selected while `HistoryLayer.tjs` needed Shift-JIS, producing `Cannot convert given narrow string to wide string`. The adapted engine passes that point, then exits at the game's `Storages.searchCD("syarin")` check. The Web implementation of `TVPSearchCD` returns an empty result; the supplied ZIP contains no mounted optical volume. Disc checks are unchanged. Title, Chinese dialogue, save/load, audio/video and a complete playthrough for this game remain unverified. This decoding fix does not establish playable compatibility for that release.

Regression: the existing real-game desktop Chromium test for the supplied Kamimaho Chinese share passed story startup, wheel history, right-click return, modal sizing/cancel, save and reload/load, Enter and blur releases with the adapted module. This is a regression check, not evidence that every game or ambiguous encoding works.
