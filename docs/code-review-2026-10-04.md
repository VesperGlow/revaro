**1. P1：恢复历史版本后，传输中的旧保存请求仍能覆盖恢复结果。已用真实 TCP 复现。**

位置：`crates/revaro-server/src/file_routes.rs:798`、`:814`、`:854`、`:860`；相关恢复实现：`crates/revaro-server/src/version_routes.rs:118`。

保存接口先查询文件，然后等待 JSON 请求体。ETag 与这份事务外的旧文件快照比较；最终 UPDATE 仅检查 `object_key`，没有检查 ETag。历史恢复会重新引用旧对象，因此文件经历 A → B → 恢复 A 时，旧对象键重新匹配，但恢复生成的新 ETag 没有参与最终校验。

复现步骤：

1. 创建内容为 A 的文档，记录 ETag A。
2. 发起携带 ETag A 的保存请求，发送 HTTP 头和部分 JSON，暂不传完请求体。
3. 用另一连接把文档保存成 B，然后恢复到 A 的历史版本。
4. 继续传完第一条请求，提交一份过时的新内容。

实际结果：恢复后的内容先是 `original A`，旧请求随后返回 `HTTP/1.1 200 OK`，内容变成 `stale request overwrote restored A`。恢复后的 ETag 已与原 ETag 不同，仍未阻止这次写入。

建议在写事务中重新验证当前 ETag，并让条件 UPDATE 同时校验读取时的 ETag 和对象键；发生变化时返回 409。补一个请求体延迟、保存、恢复、旧请求完成的回归场景。恢复中的 UUID ETag 设计可以保留。

**2. P2：全局音乐播放器从头播放，并覆盖已保存的续播位置。已用浏览器复现。**

位置：`crates/revaro-web/src/components/music_player.rs:131`、`:139`、`:170`。原音频组件有读取进度的逻辑，见 `crates/revaro-web/src/components/audio.rs:527`。

全局播放器会每隔约 5 秒保存进度，也会在暂停时保存，但切歌或打开歌曲时只清零位置并播放，没有调用 `fetch_media_progress`。这与“刷新后不恢复音乐队列”是两个不同的功能边界：即使用户主动重新选中同一首歌，已保存的单曲位置也不会恢复。

实测：为一首 90 秒 WAV 保存 60 秒位置，再从音乐库点击歌曲；播放器位置为约 0.54 秒，服务器原有 60 秒位置已经被首个 timeupdate 保存成约 0.165 秒。

建议加载歌曲时读取进度，等媒体元数据可用后应用位置，并在恢复结束前暂停自动保存。切歌期间的异步读取需要校验歌曲 ID 或 revision，避免旧请求影响当前歌曲。

**3. P2：首页“最近添加的视频”实际只显示最近打开过的视频。已用浏览器复现。**

位置：`crates/revaro-web/src/components/content_shell.rs:976`、`:990`、`:1023`。

首页只有图片库跳过 recent 查询，视频也会以“最近打开”的非空结果完全替换“最近添加”结果。

实测：上传旧视频和新视频，只把旧视频标记为已打开。正常视频库接口把新视频排在第一项；首页“最近添加的视频”只显示旧视频，新视频卡片数量为 0。这会使用户上传的新视频无法进入这个首页栏目。

建议这个栏目直接使用添加时间排序的结果；如果产品希望展示继续播放，应调整栏目的名称与内容策略。

**4. P2：最近阅读/播放排序忽略了比打开时间更新的进度时间。已用 API 复现。**

位置：`crates/revaro-server/src/library_routes.rs:97`、`:106`。

`last` 使用 COALESCE，优先选取 `library_state.last_opened`。它选的是第一个非空值，不能得到几个来源中最近的时间。文件有 last_opened 后，后续阅读或媒体进度更新不会影响最近列表排序或返回的 last_opened。

实测：先打开 B，再打开 A，最近列表为 A、B；随后更新 B 的媒体进度。B 的 progress.updated_at 已晚于 A 的打开时间，最近列表仍为 A、B，B 返回的 last_opened 仍是早先的时间。多设备或多个标签页继续阅读/播放时，会出现这一情况。

建议取打开、阅读进度、媒体进度三个时间中的最新活动时间，并统一比较格式；新增包含 last_opened 和更新进度的排序用例。

**另一个需要基准验证的性能风险：书库列表在返回前同步索引全部待索引书籍。**

位置：`crates/revaro-server/src/library_routes.rs:88`、`:161`、`:166`。

书籍查询或未指定 kind 的查询都会先执行 index_book_series；待处理查询没有数量限制，也不使用本次搜索、集合或分页范围，循环逐本读 EPUB 并解析系列信息。批量导入或首次升级后，即使只请求第一页或一个关键词，也要等全部待索引书籍处理完。首页先查询书籍，后面几个栏目也会等待这次响应。

**四项修复与回归验证**

1. 文档保存现在在写事务内检查读取时的对象键与 ETag，最终条件 UPDATE 也包含 ETag。请求体延迟期间发生保存和历史恢复时，无论客户端是否显式提供 ETag，旧请求都会返回 409，不增加历史快照、不改变已恢复的内容。原真实 TCP 复现脚本复测得到 409，内容仍为 `original A`。
2. 全局音乐播放器在保存位置和原生媒体元数据都加载完成后应用续播位置，然后播放。恢复前及切换源期间禁止保存，歌曲 ID 和 revision 阻止迟到响应影响其他歌曲或停止后的播放器；单曲循环明确从头开始。
3. 首页只有书籍和音乐查询最近活动，图片和视频直接使用最近添加的结果。
4. 内容库取打开、阅读进度、媒体进度中的最新时间。SQLite 连接注册时间规范化函数，将已有 RFC3339Nano 和 SQLite 时间转换成保留纳秒的统一比较格式，无需修改已有数据库数据。

增加 `delayed_document_saves_cannot_overwrite_a_restored_revision` 和 `recent_items_use_the_latest_activity_with_nanosecond_precision` 两项 Rust 回归测试，以及 `tests/e2e/content-regressions.spec.ts` 的三项浏览器回归；新浏览器文件已加入 CI 发布门禁。新用例使用独立目录并清理内容。
