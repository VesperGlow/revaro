**Revaro 全项目扫描报告 · 2026-10-02**

这是修改前的扫描快照。后续修复与功能交付见 [实施记录](implementation-2026-10-02.md)。

本次检查覆盖五个业务 crate、xtask、三份 SQL migration、部署配置、项目文档和现有 E2E。通过入口、路由、共享模型、前端组件及关键实现核对功能，并在独立临时数据目录启动服务验证问题。本次只新增这份报告，没有修改业务代码。

总体判断：Revaro 已具备完整的单管理员自托管文件管理闭环。它的主要特点是本地对象存储、共享 Rust 数据契约、原文件媒体播放，以及服务端清洗内容、客户端分页的阅读器。存储一致性、输入限制和任务生命周期已有较多实现与测试；下一阶段应优先修复下面的三个已复现问题，再完善大目录性能、浏览器回归测试和恢复能力。

**架构与职责**

| 模块 | 当前职责 |
|---|---|
| `revaro-core` | 前后端共享 API DTO、文件/任务/进度模型、文件分类、输入校验、对象键、大小限制、时间和哈希工具 |
| `revaro-server` | Axum HTTP 服务；账户、SQLite、上传、下载、分享、回收站、文本编辑、阅读接口、缓存和后台维护 |
| `revaro-web` | Leptos CSR/WASM 前端；登录、文件浏览、上传队列、任务中心、编辑器、图片查看、音视频播放器、阅读器及账户设置 |
| `revaro-reader` | EPUB/TXT 解析、编码处理、目录解析、内容清洗、图片资产、稳定阅读锚点和 reading flow 构建 |
| `revaro-media` | 进程内 FFmpeg 媒体探测、视频帧/音频内嵌封面、图片缩略图 |
| `xtask` | fmt、Clippy、Rust 测试、WASM 检查、前端产物及 release 服务端构建 |

持久数据分为 `/data`（SQLite 和账户配置）、`/objects`（原文件、分片、缩略图及阅读派生对象）和 `/caches`（可重建工作缓存）。文件夹结构由数据库表示，原文件以 UUID blob 存储。文件副本共享同一个 blob，编辑文档则写入新 blob 后切换元数据引用。

这不是服务器现有目录的直接浏览界面；当前文件主要通过应用上传进入系统。备份需要同时保存数据库与对象卷。

**优先修复：已确认的问题**

1. **P1：初始管理员密码输出到日志，凭据文件没有生成。**

   代码位置：`crates/revaro-server/src/main.rs:72`，文档：`README.md:15`。README 说随机密码写入 `/data/initial-admin-credentials`，权限 0600；主程序实际把密码作为 tracing 字段输出，仓库没有创建该文件的代码。独立空数据库启动的结果是 `credential_file_exists=False`、`password_written_to_log=True`。这既扩大了密码在容器日志/日志收集系统中的暴露范围，也使文档中的首次登录步骤失效。

   建议完成 0600 凭据文件交付，日志只报告路径；处理凭据文件写入失败及初始化中断后的恢复，并为真实启动流程补测试。仅修改 README 无法解决日志明文密码的问题。

2. **P1：EPUB 副本的书内图片地址绑定原文件 ID。**

   代码位置：`crates/revaro-server/src/reader_routes.rs:85`、`:130`、`:533`，以及 `crates/revaro-server/src/file_routes.rs:2290`。复制共享 object key，解析书籍和持久 flow 也按 object key 共享；但是解析过程中已经将图片地址写成 `/api/files/{首次打开文件ID}/book/assets/...`。

   复现：上传含图 EPUB → 打开原书生成 flow → 复制 → 打开副本 → 将原书移入回收站并永久删除。副本 chunk 返回 200，chunk 内仍是原书的图片地址，该地址返回 404；换成副本自己的 assets 地址则返回 200。原文件仅软删除时仍可读取，所以永久删除才使这个问题明显出现。

   建议共享解析内容保存文件无关的资产标识，在当前阅读上下文绑定资源地址。若选择按 file ID 隔离缓存，需要同时调整解析缓存和持久 flow，不能只改 LRU key。修复应升级 flow 格式版本，避免旧派生文件继续复用错误地址；覆盖复制、原书删除和服务重启场景。

3. **P1：公开分享并发许可没有覆盖响应体传输。**

   代码位置：`crates/revaro-server/src/file_routes.rs:2033`、`:2133`。代码将许可放入 response extensions，希望下载结束才释放；真实 HTTP 栈在发送响应头阶段处理并丢弃这些 extensions，响应体仍继续发送，许可已经释放。

   复现：在独立测试对象卷创建 128 MiB 文件，用 12 个 HTTP 连接顺序取得响应头并保持响应体不消费。12 个请求全部返回 200，超过配置在代码中的 8 个活动传输上限。这个问题不会被仅检查 Router 返回对象的测试发现。

   建议让许可由响应体/流持有，直到传输完成或连接断开；用真实 TCP 慢客户端验证第 9 个活动请求收到 429，以及断开连接后许可被释放。

4. **P2：刷新后任务中心“重试”可能只改变状态，没有恢复传输。**

   代码位置：`crates/revaro-web/src/components/tasks.rs:256`、`crates/revaro-server/src/file_routes.rs:1106`。本地 UploadController 找不到文件任务时，前端回退调用服务端重试接口；该接口把 failed 改成 retrying/queued 并返回 202，没有上传文件读取与传输执行器。

   独立测试将未完成上传的任务置为 failed 后调用重试，得到 202 和 `('retrying','queued')`。结合实现可确认：没有浏览器 File 句柄时，这个状态更新本身不会重新上传文件。

   建议显示“重新选择原文件以继续”，使用 waiting_input 状态表达等待文件，匹配已上传分片后恢复；重新上传真正开始时再进入 running。不要让缺少本地文件的任务长期显示为已排队执行。

5. **P2：负数保留时间被静默转换为 0。**

   代码位置：`crates/revaro-server/src/config.rs` 的 `parse_duration`、`from_lookup` 和 `accepts_negative_trash_and_gc_values_when_the_duration_parses` 测试。`TRASH_RETENTION=-1h` 被接受并变为 0，回收站维护对 0 的处理是关闭自动清理；`GC_INTERVAL` 也会发生类似情况。FLOW_CACHE_TTL 的负数校验另外依赖未 trim 原值的前缀检查，语义不统一。

   建议统一拒绝负数，仅明确允许的配置接受显式 0；同样统一 URL 解析及空白处理。这个问题当前会意外关闭清理，而不是立即清空回收站。

**性能、维护和产品改进建议**

下面是根据代码结构提出的增强项，没有做压力基准，也不将它们列为已复现故障。

| 优先级 | 建议 | 代码依据与预期收益 |
|---|---|---|
| P2 | 大目录分页/游标 + 前端窗口渲染 | `children` 将全部子项装入 Vec 返回，网格渲染整个 items；万级文件会增加数据库结果、JSON 和 DOM 开销 |
| P2 | 阅读解析与 ZIP 生成的全局并发预算 | 阅读器仅按书加锁，没有全局解析/flow 构建并发上限；ZIP 每次启动 blocking worker；LRU 容量不限制在途解析的峰值内存 |
| P2 | 慢上传超时及磁盘空间预检 | 上传流等待期间持有 upload 锁；当前单文件大小上限不等于磁盘总量控制；应区分总超时、无进展超时和分片大小 |
| P2 | 备份/恢复工具与管理员恢复入口 | 当前只有手动停服备份说明，忘记密码时没有接入主程序的 reset 命令；恢复演练比单独增加备份按钮更重要 |
| P2 | 增加真实浏览器回归 | 现有 E2E 只有 5 项，重点覆盖媒体查看/移动/复制、编辑器和短 EPUB；补分片、取消/续传、分享、回收站、TOTP、长章、字号重排和移动触摸场景 |
| P2 | 确认并更新阅读器文档的测试覆盖描述 | `docs/reader-flow.md` 宣称重排、缓存、深链等当前 E2E 覆盖，但现有测试文件未包含对应独立用例；窗口大小描述也存在早期方案残留 |
| P2 | 批量操作逐项结果与安全重试 | 前端逐项移动/删除/恢复可能部分成功，应明确成功/失败项；不宜在出错后笼统显示整批失败 |
| P2 | 浏览器阅读缓存上限及清理入口 | `reader_cache.rs` 没有跨书容量/条目/TTL 策略，也没有登出清理；长期使用可能持续积累旧 manifest 和 HTML chunk |
| P2 | 曝光已有运行统计 | CacheManager 与 MaintenanceRuntime 已有统计基础，但界面/API 没有缓存命中、清理失败、磁盘余量、任务耗时等运维视图 |
| P3 | 搜索与排序 | 先增加文件名搜索、大小/时间排序，再依据需求决定全文检索；保留现在的简洁文件浏览布局 |
| P3 | 分享到期时间与分享总览 | 单管理员也需要能找回所有有效链接、快速撤销，并避免永久遗留的公开链接 |
| P3 | 文本历史或保存前版本保留 | 文档保存写入新对象后旧引用被安排回收；可增加少量版本/撤销能力，降低误覆盖的恢复成本 |
| P3 | 提升目录操作完整性 | 按需求加入递归复制和目录 ZIP；需要数量、体积、取消与部分失败限制 |
| P3 | 拆分大型模块 | 前端 reader 3,039 行、file_browser 2,689 行、uploads 1,526 行；后端 file_routes 3,708 行包含约 1,300 行测试。优先按状态/动作/视图和文件/文档/分享/回收站拆分 |
| P3 | 清理迁移兼容负担 | 注释和 DTO 中仍有较多 Go/Vue reference 及历史空值兼容逻辑；先确定旧客户端支持范围，再简化，避免为了重构破坏已有数据 |

拆分文件时，应把稳定规则留在纯逻辑层，让 DOM、异步生命周期、数据库事务和 HTTP 响应各自有明确边界。共享 Rust 契约是现有优势，应保留。

值得保持的实现还有：流式上传和下载；文档写入后使用条件 UPDATE 避免并发保存覆盖；文件清理与数据库删除在同一事务入队；对象原子提交；media KDF/解码预算；EPUB 解压及渲染限制；Markdown/EPUB 清洗；Origin 校验、SameSite Cookie、安全响应头和公开分享 sandbox。
